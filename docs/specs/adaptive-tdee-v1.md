# Adaptive TDEE and Nutrition Coaching v1

**Status:** Development-ready specification<br>
**Owner:** Pulse<br>
**Version:** 1.0<br>
**Algorithm version:** `adaptive-tdee-v1`<br>
**Last updated:** 2026-08-12

## 1. Purpose

Pulse will add an adaptive nutrition-coaching feature that:

1. Produces an initial resting metabolic rate (RMR) and total daily energy expenditure (TDEE) estimate from profile data.
2. Learns a personalized TDEE from logged calorie intake and body-weight trend.
3. Recommends calorie and macronutrient targets for a configured rate of weight loss, maintenance, or weight gain.
4. Offers a weekly check-in and a user-triggered **Check in now** action.
5. Never silently changes nutrition targets in v1. The user must accept a recommendation.
6. Explains the data and calculations behind every recommendation.
7. Holds the current estimate rather than inventing an update when data are insufficient or suspect.

The feature is not a medical device and does not claim to measure basal metabolism. Food intake and body-weight change can estimate effective maintenance expenditure, not “true BMR.” MacroFactor describes the same high-level energy-balance approach: estimated expenditure is derived from calorie intake and change in trended weight.[1]

## 2. Terminology

| Term                   | Definition in Pulse                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| RMR                    | Resting metabolic rate estimated during setup with Mifflin-St Jeor. Used only as an initial input and plausibility reference. |
| Baseline TDEE          | Initial TDEE calculated from estimated RMR and an activity multiplier, or supplied manually.                                  |
| Observed TDEE          | TDEE inferred from average logged intake and change in trended weight over the analysis window.                               |
| Adaptive TDEE          | Persisted, smoothed estimate used for coaching recommendations.                                                               |
| Scale weight           | A raw body-weight entry.                                                                                                      |
| Trend weight           | Smoothed daily weight series used to reduce short-term water and gastrointestinal noise.                                      |
| Complete nutrition day | A date the user explicitly confirms includes all calorie-containing intake.                                                   |
| Check-in               | An immutable calculation snapshot that may be pending, accepted, declined, superseded, or held.                               |
| Recommendation         | Proposed calories and macros generated by a check-in.                                                                         |
| Program                | The active goal, baseline, macro preferences, and coaching configuration for one user.                                        |

User-facing copy must say **Estimated RMR**, **Starting expenditure**, and **Adaptive TDEE** or **Personalized expenditure**. It must not say “true BMR,” “measured metabolism,” or “exact maintenance calories.”

## 3. Why the Algorithm Uses Kilograms

All adaptive calculations use canonical metric units internally:

- Weight: kilograms
- Height: centimeters
- Energy: kilocalories
- Time: calendar days

Mifflin-St Jeor is conventionally expressed using kilograms and centimeters, and the v1 stored-energy coefficient is expressed as kilocalories per kilogram.[6] Using one canonical unit prevents a user preference change from turning `180 lb` into `180 kg` or mixing pounds and kilograms inside a calculation.

Pulse may display pounds or kilograms according to `users.weightUnit`. Conversion occurs only at API/UI boundaries:

```text
kg = lb × 0.45359237
lb = kg ÷ 0.45359237
```

All persisted adaptive calculation inputs and outputs use kilograms. Display values are derived and must never be fed back into the algorithm without explicit conversion.

## 4. Goals and Non-goals

### 4.1 Goals

- Functional, deterministic coaching for one or many isolated Pulse users.
- Transparent calculations that can be replayed from persisted inputs.
- Safe behavior under missing, stale, partial, noisy, or corrected data.
- Historical nutrition targets that remain correct for past dates.
- Idempotent weekly and manual check-ins.
- Pure algorithm code with comprehensive unit and fixture tests.
- Unified JWT and AgentToken API support unless a route explicitly changes account-level configuration.

### 4.2 Non-goals for v1

- Estimating exercise calories from workouts or wearables.
- Measuring BMR or replacing indirect calorimetry.
- Body-fat, lean-mass, menstrual-cycle, or body-recomposition modeling.
- Full NIH dynamic differential-equation modeling.
- Different calorie targets for training and rest days.
- Automatic target acceptance.
- Push notifications, email, or external scheduler infrastructure.
- Machine learning or opaque heuristics.
- Pediatric, pregnancy, breastfeeding, or clinical-diet support.

## 5. Product Principles

1. **Adherence-neutral:** use actual intake, not the difference between intake and the previous target. A user can miss the target and still receive a valid update.[1]
2. **No partial-day guessing:** an explicitly partial day is never treated as a low-calorie complete day.
3. **Trend before reaction:** use smoothed weight rather than week-to-week raw scale differences.[2]
4. **Hold before harm:** insufficient or implausible data produce a specific hold reason.
5. **User approval:** recommendations are proposals until accepted.
6. **Auditability:** every accepted adaptive target links to the exact check-in that produced it.
7. **Determinism:** the same algorithm version, program, prior estimate, and data fingerprint produce the same result.
8. **Local-date correctness:** “today,” weekly due dates, nutrition dates, and target effective dates use the program’s IANA time zone.

## 6. Existing Pulse Capabilities and Required Changes

### 6.1 Existing capabilities to reuse

- `nutrition_logs`, `meals`, and `meal_items` preserve dated calorie and macro snapshots.
- `body_weight` preserves one weight per user and date.
- `nutrition_targets` is already effective-dated.
- `/api/v1/nutrition/:date/summary` aggregates daily intake.
- Dashboard macro and weight trend endpoints already aggregate historical data.
- Settings already edits manual nutrition targets.
- Shared Zod schemas are the source of truth for API contracts.

### 6.2 Existing behavior that must not be reused as-is

- `NutritionWeekDaySummary.completeness` measures progress toward calorie/protein targets. It does **not** establish that all food was logged.
- `computeEWMA` currently runs only on supplied entries and does not interpolate missing dates. Adaptive TDEE requires its own pure trend pipeline or an extended utility with explicit interpolation semantics.
- `body_weight.weight` has no canonical stored unit.
- Current target creation uses a UTC date in the web settings page.
- Current target mutation invalidates only target queries; adaptive acceptance must invalidate all affected summaries and dashboard data.

| Target weight          | preferred display unit                          | Required for lose/gain; optional for maintain; persist kg                                   |

Setup preview displays:

- Estimated RMR, unless manual TDEE mode
- Activity multiplier
- Starting TDEE
- Initial goal calories
- Initial protein, carbohydrate, and fat targets
- Warning that personalization generally requires multiple weeks of complete nutrition and weight data

Submitting setup:

1. Creates the program.
2. Creates the first check-in with `kind = baseline` and `status = pending`.
3. Does not alter current nutrition targets until the user selects **Use these targets**.
4. Accepting creates a target effective on the program’s local date.

Setup cannot calculate RMR, goal-rate calories, target direction, or default protein without weight. It uses a weight entered in setup or the latest canonical saved weigh-in when that entry is no more than seven local calendar days old. Otherwise setup returns `NO_CURRENT_WEIGHT` and creates neither a program nor a baseline check-in. A setup-entered weight is written to body-weight history for the setup local date in the same transaction.

### 7.5 Nutrition day completion

Past and current nutrition log views gain a completion control:

- `Unknown`: legacy/default state; excluded from the algorithm
- `Partial`: user confirms the day is incomplete; excluded
- `Complete`: user confirms all calorie-containing intake is represented; eligible

Rules:

1. A day with no nutrition log cannot be marked complete.
2. A date in the future cannot be marked complete.
3. Today may be marked complete, but the action warns that later food changes will require reconfirmation.
4. Creating, editing, appending, or deleting a meal/item on a complete day automatically changes the day to `partial`.
5. The UI explains that estimated restaurant meals are acceptable; omitted meals are not.
6. Bulk completion is out of scope for v1.

### 7.6 Weekly behavior

No cron or worker is added.

A check-in is due when:

```text
localDate >= lastWeeklyAttemptLocalDate + 7 calendar days
```

`lastWeeklyAttemptLocalDate` is the local date of the latest check-in with `kind = weekly`, including `held`, `accepted`, `declined`, or `superseded`. If no weekly check-in exists, use program creation date. A held weekly attempt therefore clears the due badge for seven days while leaving the prior Adaptive TDEE unchanged. Manual check-ins do not move the weekly schedule.

When the Coach page or dashboard summary loads:

- The read endpoint reports `checkInDue`.
- The UI shows a badge.
- It does not create a check-in merely from a read.
- Opening Coach while due may automatically call the preview mutation once per browser session.
- **Check in now** always requests a preview, even when not due.

Manual and weekly previews use identical calculations.

## 8. Initial Baseline Calculation

### 8.1 Estimated RMR

For `mifflin_male`:

```text
estimatedRmrKcal = 10 × weightKg + 6.25 × heightCm - 5 × ageYears + 5
```

For `mifflin_female`:

```text
estimatedRmrKcal = 10 × weightKg + 6.25 × heightCm - 5 × ageYears - 161
```

The Academy of Nutrition and Dietetics recommends Mifflin-St Jeor when measured RMR is unavailable and describes applying a physical-activity factor to estimate total needs.[6]

Age is the integer age on the program calculation’s local date, not `currentYear - birthYear`.

### 8.2 Activity levels

| Key           | Multiplier | User-facing description                                    |
| ------------- | ---------: | ---------------------------------------------------------- |
| `sedentary`   |       1.20 | Mostly seated daily life; little purposeful activity       |
| `low_active`  |      1.375 | Light daily movement or several training sessions per week |
| `active`      |       1.55 | Consistently active daily life and regular training        |
| `very_active` |      1.725 | High daily movement, demanding training, or physical work  |

These are starting priors, not permanent claims about activity. Formula-based starting estimates can be materially wrong for an individual, which is why Pulse must permit a manual override and transition to intake-and-weight-derived expenditure as eligible data accumulate.[5]

### 8.3 Baseline TDEE

```text
calculatedBaselineTdee = estimatedRmrKcal × activityMultiplier
baselineTdee = manualOverrideKcal ?? calculatedBaselineTdee
```

Round persisted and displayed baseline TDEE to the nearest whole kcal. Preserve the unrounded RMR and intermediate multiplication in the baseline check-in input snapshot for replay.

Manual TDEE validation: 800–8,000 kcal/day.

## 9. Analysis Window and Input Eligibility

### 9.1 Date boundaries

All boundaries use the program’s IANA time zone.

For a preview generated on local date `D`:

```text
analysisEnd = D - 1 day
```

If the user explicitly completed today and manually presses **Check in now**, the request may set `includeToday = true`, making `analysisEnd = D`. Automatic weekly previews never include today.

```text
analysisStart = analysisEnd - 20 days
weightWarmupStart = analysisEnd - 41 days
```

The primary analysis window is 21 calendar days. Weight data use up to 21 additional days for trend initialization.

### 9.2 Nutrition eligibility

A nutrition date is usable when:

- `nutrition_logs.status = complete`
- Its date is within the final usable weight-trend range
- It has at least one meal item
- Total calories are finite and greater than zero

Minimum:

```text
completeNutritionDayCount >= 12
```

Calculate average intake only from complete dates:

```text
averageIntakeKcal = arithmeticMean(completeDayCalories)
```

Do not treat absent, `unknown`, or `partial` dates as zero. Do not impute calories in v1. The assumption is that at least 12 complete days are representative of the 21-day period. Confidence is reduced for lower coverage, and the UI lists excluded dates. MacroFactor similarly emphasizes frequent nutrition logging and notes that nutrition gaps are harder to estimate than weight gaps.[4]

### 9.3 Weight eligibility

Within `weightWarmupStart ... analysisEnd`:

- At least 3 actual weigh-ins
- Actual weigh-ins span at least 14 calendar days
- Latest weigh-in is no more than 7 days before `analysisEnd`
- At least one actual weigh-in lies on or before `analysisStart + 7 days`
- At least one lies on or after `analysisEnd - 7 days`

Weights outside `25–350 kg` are rejected by the write schema after canonical conversion.

### 9.4 Suspect-weight hold

Before interpolation, sort actual weigh-ins. Hold with `SUSPECT_WEIGHT_DATA` if either condition is true:

1. Adjacent entries no more than 3 days apart differ by more than 5% of the earlier weight.
2. A single entry differs by more than 5% from the median of actual entries within ±7 days and the following actual entry returns within 2% of that local median.

The response identifies suspect entry IDs and dates. The algorithm does not silently delete, winsorize, or correct user data.

### 9.5 Stale history

Historical data older than the analysis window may be used only for EWMA warmup. April data cannot produce an August personalized update.

If a prior Adaptive TDEE exists but current data are ineligible, return `holding` with the prior estimate and a reason. If no prior adaptive estimate exists, return `learning` and the baseline.

## 10. Weight Trend Algorithm

### 10.1 Canonical input

Use `{ date, weightKg, sourceEntryId | null, interpolated }`.

### 10.2 Interpolation

Between each pair of actual weigh-ins, generate one point per missing calendar date using linear interpolation:

```text
interpolatedWeight = leftWeight
  + ((date - leftDate) / (rightDate - leftDate))
  × (rightWeight - leftWeight)
```

Do not extrapolate before the first or after the last actual weigh-in. MacroFactor publicly describes linear interpolation for missing scale-weight dates.[2][3]

### 10.3 EWMA

Apply an exponentially weighted moving average to the daily actual/interpolated series.

Use a seven-day half-life:

```text
EWMA_HALF_LIFE_DAYS = 7
alpha = 1 - exp(ln(0.5) / 7)
alpha ≈ 0.0942763357

trend[0] = scale[0]
trend[t] = alpha × scale[t] + (1 - alpha) × trend[t - 1]
```

The warmup series reduces initialization bias. Persist `alpha` and half-life in each check-in’s algorithm snapshot.

### 10.4 Regression slope

Select trend points whose dates fall in `analysisStart ... analysisEnd`. Require at least 14 daily trend points.

Let `x` be integer days since the first selected point and `y` be trend weight in kg. Calculate ordinary least-squares slope:

```text
slopeKgPerDay = Σ((x - meanX)(y - meanY)) / Σ((x - meanX)^2)
trendChangeKgPerWeek = slopeKgPerDay × 7
```

Do not use `lastTrend - firstTrend` as the slope. Regression uses all daily points and is less sensitive to endpoint noise.

## 11. Observed and Adaptive TDEE

### 11.1 Stored-energy approximation

```text
ENERGY_DENSITY_KCAL_PER_KG = 7700
storedEnergyChangeKcalPerDay = slopeKgPerDay × 7700
observedTdeeKcal = averageIntakeKcal - storedEnergyChangeKcalPerDay
```

Sign behavior:

- Positive slope means energy is being stored, so TDEE is lower than intake.
- Negative slope means stored energy is decreasing, so TDEE is higher than intake.
- Zero slope makes TDEE equal average intake.

The 7,700 kcal/kg coefficient is a transparent short-window approximation, not a universal long-term rule. The NIH Body Weight Planner uses a dynamic model because expenditure and body composition adapt over time.[8] Weekly re-estimation partly captures those changes, but this limitation must appear in engineering docs and About/help copy.

### 11.2 Observed-TDEE plausibility

If estimated RMR exists, hold with `IMPLAUSIBLE_EXPENDITURE` when:

```text
observedTdeeKcal < estimatedRmrKcal × 0.8
or
observedTdeeKcal > estimatedRmrKcal × 3.0
```

For manual-TDEE programs without estimated RMR, hold when:

```text
observedTdeeKcal < 800 or observedTdeeKcal > 8000
```

Return the computed value for debugging, but do not use it in a recommendation.

### 11.3 Confidence score

Calculate four components in `[0, 1]`:

```text
nutritionCoverage = completeNutritionDayCount / 21
weightFrequency = min(actualWeighInCount / 7, 1)
weightSpan = min(actualWeightSpanDays / 21, 1)

if latestWeightAgeDays <= 2: weightRecency = 1
else: weightRecency = max(0, 1 - ((latestWeightAgeDays - 2) / 5))
```

Then:

```text
confidence = clamp01(
  0.55 × nutritionCoverage
  + 0.20 × weightFrequency
  + 0.15 × weightSpan
  + 0.10 × weightRecency
)
```

Display labels:

| Score       | Label      |
| ----------- | ---------- |
| `< 0.60`    | Developing |
| `0.60–0.79` | Moderate   |
| `>= 0.80`   | High       |

Eligibility is independent of the label. An eligible estimate may be Developing.

### 11.4 Prior selection

```text
priorTdee = latest accepted adaptiveTdeeKcal
  ?? program.baselineTdeeKcal
```

Declined or pending check-ins never become the prior.

### 11.5 Confidence blend and update smoothing

```text
confidenceBlendedTdee = priorTdee
  + confidence × (observedTdeeKcal - priorTdee)

requestedTdeeDelta = 0.35 × (confidenceBlendedTdee - priorTdee)
limitedTdeeDelta = clamp(requestedTdeeDelta, -150, 150)
adaptiveTdeeKcal = roundToNearest10(priorTdee + limitedTdeeDelta)
```

Persist requested and limited deltas and whether the ±150 kcal limiter applied. MacroFactor describes adding smoothing so short-term fluctuations do not pass one-for-one into recommendations.[9]

### 11.6 No-op threshold

If `abs(adaptiveTdeeKcal - priorTdee) < 10`, set the proposed Adaptive TDEE equal to `priorTdee`. The check-in may still recommend different calories if the goal configuration changed.

## 12. Goal Calories and Safety Guardrails

### 12.1 Goal-rate storage

Persist signed `goalRatePctPerWeek`:

- Loss: negative
- Maintenance: zero
- Gain: positive

Validation:

| Goal       | Allowed rate                       |
| ---------- | ---------------------------------- |
| `lose`     | `-1.0` through `-0.1` percent/week |
| `maintain` | exactly `0`                        |
| `gain`     | `0.1` through `0.5` percent/week   |

The UI presents positive magnitudes but the API persists a signed rate. Percentage-based rates scale with body weight as it changes.[9]

### 12.2 Goal energy adjustment

Use latest trend weight at `analysisEnd`. During baseline, use latest scale weight.

```text
desiredChangeKgPerDay = trendWeightKg
  × (goalRatePctPerWeek / 100)
  / 7

goalEnergyAdjustmentKcal = desiredChangeKgPerDay × 7700
rawGoalCalories = adaptiveTdeeKcal + goalEnergyAdjustmentKcal
```

### 12.3 Deficit limit

For loss:

```text
minimumByDeficit = adaptiveTdeeKcal × 0.75
```

The recommendation may not exceed a 25% estimated deficit.

### 12.4 Calorie floor

Program setup calculates:

```text
systemCalorieFloor = max(1200, roundToNearest10(baselineTdeeKcal × 0.60))
```

The user may set `userCalorieFloorKcal >= systemCalorieFloor`. v1 does not allow lowering the system floor in the UI or API.

For loss:

```text
minimumAllowedCalories = max(systemCalorieFloor, userCalorieFloor, minimumByDeficit)
```

If `rawGoalCalories < minimumAllowedCalories`, propose `minimumAllowedCalories`, add `CALORIE_FLOOR_APPLIED`, and calculate `achievableGoalRatePctPerWeek` from the limited calories. The UI says the selected rate is not supported by current guardrails.

Apply bounds before persisted-value rounding:

```text
boundedGoalCalories = max(rawGoalCalories, minimumAllowedCalories) // loss
persistedGoalCalories = ceil(boundedGoalCalories / 10) × 10       // constrained loss
```

Rounding a constrained loss recommendation upward ensures the persisted target cannot cross below either the calorie floor or 25% deficit minimum. For an unconstrained loss result, maintenance, or gain, use ordinary nearest-10 rounding. Calculate `achievableGoalRatePctPerWeek` from the final persisted calories, then allocate macros from that value.

This is a product guardrail, not a clinical prescription.

### 12.5 Recommendation-change limiter

The ±150 kcal limiter applies to Adaptive TDEE, not separately to goal calories. A deliberate goal-rate or goal-type change may therefore change recommended calories by more than 150 kcal. The comparison must attribute the difference to:

- Expenditure change
- Goal change
- Guardrail change

If the goal configuration did not change, proposed calories should normally move by no more than the Adaptive TDEE delta, except when a floor starts or stops binding.

### 12.6 Goal completion

For lose/gain goals, define tolerance:

```text
goalToleranceKg = max(0.23, targetWeightKg × 0.0025)
```

This is approximately 0.5 lb or 0.25% of target weight, whichever is larger.

A goal is reached when:

- Lose: `trendWeightKg <= targetWeightKg + goalToleranceKg`
- Gain: `trendWeightKg >= targetWeightKg - goalToleranceKg`

When reached, return `goalReached = true` and propose maintenance calories at Adaptive TDEE. Acceptance changes the program goal to `maintain`, sets rate to zero, and retains target weight as the maintenance center.

### 12.7 Maintenance behavior

v1 maintenance target is exactly Adaptive TDEE. Dynamic maintenance bands and corrective surplus/deficit nudges are deferred.

## 13. Macro Allocation

### 13.1 Protein

Protein is a program preference and remains fixed between check-ins unless the user changes it. The Coach page displays g/kg based on current trend weight.

The default is:

```text
proteinGrams = roundToNearest5(currentTargetProtein ?? 1.8 × currentWeightKg)
```

Validation: 40–400 g/day.

The ISSN position stand reports 1.4–2.0 g/kg/day as sufficient for most exercising individuals.[7] Pulse does not automatically diagnose or enforce an “optimal” value.

### 13.2 Fat and carbohydrates

```text
proteinKcal = proteinGrams × 4
fatGrams = roundToNearest5((goalCalories × fatAllocationPct / 100) / 9)
remainingKcal = goalCalories - proteinKcal - fatGrams × 9
carbGrams = round(remainingKcal / 4)
```

Validation fails with `MACRO_CONFIGURATION_INFEASIBLE` if `remainingKcal < 0`.

After calculating integer carbs:

```text
macroCalories = proteinGrams × 4 + carbGrams × 4 + fatGrams × 9
macroCalorieDifference = goalCalories - macroCalories
```

Require `abs(macroCalorieDifference) <= 2`. If needed, increment or decrement carbohydrates by 1 g to minimize the difference. Persist both target calories and macro-derived calories because food labels and rounded macros may still differ slightly.

### 13.3 Accepted target precision

Persist target values as whole numbers even though existing columns are `real`:

- Calories: nearest 10 kcal, except a constrained loss minimum rounds up as specified in section 12.4
- Protein: nearest 5 g
- Fat: nearest 5 g
- Carbohydrates: nearest 1 g

### 14.5 Canonical body weight migration

Add `weightKg REAL` to `body_weight` and make it the source of truth for every weight reader, not only the adaptive algorithm.

Migration procedure:

1. Add nullable `weight_kg` and `unit_at_entry`.
2. Run a mandatory preflight that inventories every user, current `weightUnit`, value range, known deployment history, and any evidence of prior preference changes.
3. Produce an explicit reviewed migration map `{ userId: "lbs" | "kg" }`. A deployment may supply a verified default only when every affected user is known to share that unit. Abort migration when any user is ambiguous; do not infer silently from current preference alone.
4. Backfill each row through its user's reviewed map and set `unitAtEntry` to that migration unit. For the currently verified Pulse production user, the expected mapping is pounds and known values around 177–182 must become approximately 80–83 kg.
5. In the same release, atomically migrate every reader (weight history, dashboard trend, agent context, habits/resolvers, exports, and tests) to read `weightKg` and convert to the authenticated user's current display unit at the response boundary.
6. Keep legacy `weight` through v1 only as a fixed **pounds** compatibility column. Every new write converts canonical kg back to pounds for this column regardless of request or display unit. No production calculation or current reader may consume it.
7. New writes record the actual request unit in `unitAtEntry`; when omitted, use the authenticated user's current `weightUnit`.
8. Adaptive code and all other server-side calculations read only `weightKg`.

Update weight write contracts to accept optional `unit`; default to the authenticated user’s `weightUnit`. Responses derive `weight` from canonical kg in the user's current display unit. Keep `weightKg` internal unless a public API need is established.

Before production migration, take and verify a database backup. Do not deploy the migration if backup verification fails.

## 15. API Contract

All routes live under `/api/v1/adaptive-nutrition` and use standard envelopes.

### 15.1 `GET /api/v1/adaptive-nutrition`

Auth: JWT or AgentToken.

Returns current state without creating a check-in:

```json
{
  "data": {
    "state": "learning",
    "program": {},
    "currentTarget": {},
    "latestAcceptedCheckIn": null,
    "pendingCheckIn": null,
    "checkInDue": false,
    "nextCheckInDate": "2026-08-19",
    "eligibility": {
      "eligible": false,
      "completeNutritionDays": 1,
      "requiredCompleteNutritionDays": 12,
      "weighIns": 0,
      "requiredWeighIns": 3,
      "weightSpanDays": 0,
      "requiredWeightSpanDays": 14,
      "latestWeightAgeDays": null,
      "reasonCodes": ["INSUFFICIENT_NUTRITION", "INSUFFICIENT_WEIGHT"]
    }
  }
}
```

### 15.2 `PUT /api/v1/adaptive-nutrition/program`

Auth: JWT only for v1 because this changes account-level coaching configuration.

Creates or updates the active program. A calculation-affecting update supersedes any pending check-in. Updating profile fields recalculates baseline fields only when `rebaseline: true`; otherwise existing baseline remains stable.

Errors:

- `400 ADAPTIVE_PROGRAM_INVALID`
- `400 GOAL_TARGET_DIRECTION_INVALID`
- `400 CALORIE_FLOOR_TOO_LOW`
- `400 MACRO_CONFIGURATION_INFEASIBLE`
- `409 PENDING_CHECKIN_EXISTS` when caller does not allow superseding

### 15.3 `POST /api/v1/adaptive-nutrition/check-ins/preview`

Auth: JWT or AgentToken.

Body:

```json
{
  "kind": "manual",
  "includeToday": false
}
```

Behavior:

1. Read program, current target, prior accepted check-in, nutrition logs/items, and canonical weights in one consistent transaction/read snapshot.
2. Build canonical sorted input snapshot.
3. Hash canonical JSON with SHA-256.
4. Return an existing `pending` check-in if `(programId, fingerprint, version)` matches. For an identical held calculation, reuse a `held` row only when `kind` and `localDate` also match.
5. Otherwise calculate the new result. If it is actionable, supersede an older pending check-in with a different fingerprint before inserting the replacement within the same immediate transaction.
6. Insert the new pending or held check-in. Terminal `accepted`, `declined`, or `superseded` rows are never reopened or returned as a new actionable preview.

Held/learning calculations return 200 with a persisted `held` check-in and reason codes. Invalid configuration returns 400.

### 15.4 `POST /api/v1/adaptive-nutrition/check-ins/:id/accept`

Auth: JWT only for v1.

Body:

```json
{
  "replaceSameDateTarget": false
}
```

Transaction:

1. Verify ownership and branch on status: `pending` continues; `accepted` returns 200 with its existing accepted target; `declined`, `superseded`, or `held` returns `409 CHECKIN_NOT_ACCEPTABLE`.
2. Verify program algorithm version still matches.
3. Recompute the fingerprint using the check-in's persisted `localDate`, `analysisStart`, `analysisEnd`, `includeToday`, algorithm constants, and prior reference while re-reading mutable source rows for those exact ranges. Crossing local midnight alone must not stale a preview.
4. If fingerprint changed, return `409 CHECKIN_STALE` and do not write a target.
5. Resolve same-date target conflict.
6. Upsert nutrition target with `source = adaptive` and check-in ID.
7. If `goalReached`, update program to maintenance.
8. Mark check-in accepted and set target ID/resolution time.
9. Commit atomically.

Invalidate frontend query families:

- Adaptive nutrition
- Nutrition targets
- Daily nutrition summaries
- Nutrition week summaries
- Dashboard snapshot
- Dashboard macro trends
- Agent context where applicable

### 15.5 `POST /api/v1/adaptive-nutrition/check-ins/:id/decline`

Auth: JWT only.

Marks pending check-in declined. Does not modify targets or prior Adaptive TDEE. A repeated decline of the same declined check-in returns 200; accepted, superseded, or held check-ins return `409 CHECKIN_NOT_DECLINABLE`.

### 15.6 `GET /api/v1/adaptive-nutrition/check-ins`

Auth: JWT or AgentToken.

Paginated newest-first history. Default 20, max 100. List payload is compact; omit full daily snapshots.

### 15.7 `GET /api/v1/adaptive-nutrition/check-ins/:id`

Auth: JWT or AgentToken. Returns full replay/audit detail.

### 15.8 `PATCH /api/v1/nutrition/:date/status`

Auth: JWT or AgentToken.

Body:

```json
{ "status": "complete" }
```

Errors:

- `400 FUTURE_NUTRITION_DATE`
- `409 NUTRITION_LOG_REQUIRED`

Nutrition meal/item mutations call a shared store helper that changes complete logs to partial in the same transaction as the data mutation.

## 17. Determinism and Fingerprinting

Canonical fingerprint input includes:

- Algorithm version and constants
- Program calculation fields
- Prior accepted Adaptive TDEE/check-in ID
- Current nutrition target
- Analysis boundaries and `includeToday`
- Every nutrition date in range with status and complete-day calorie total
- Every canonical weight entry in warmup range with ID, date, kg, and updated timestamp

Canonicalization rules:

- Sort object keys recursively.
- Sort nutrition and weight arrays by date, then ID.
- Serialize numbers using JSON numeric representation after rounding canonical weight kg to 8 decimal places.
- Exclude database-created timestamps that do not affect calculation, except source row `updatedAt` values needed to detect corrections.

The fingerprint is SHA-256 lowercase hexadecimal.

A stale preview can never be accepted. Editing a meal, completion status, weight, program, or current same-date target changes the fingerprint.

## 18. Transactions and Concurrency

- Preview creation uses an explicitly configured SQLite immediate transaction to build inputs, supersede an existing pending row, and insert the check-in. Do not assume ordinary `db.transaction(...)` is immediate; use the underlying better-sqlite3 immediate transaction mode or a separately proven compare-and-swap implementation.
- Acceptance uses the same explicit immediate transaction strategy to serialize target acceptance.
- Partial unique pending-fingerprint constraints make concurrent identical actionable previews converge on one check-in without preventing valid reuse after terminal states.
- Only one pending check-in may exist per program. Enforce with a SQLite partial unique index on `programId WHERE status = 'pending'`, plus store-level handling of the resulting constraint race.
- If two accepts race, one succeeds; the other receives the resolved check-in idempotently if it targeted the same check-in.
- Add integration tests against real SQLite with two connections; mocked transaction tests are insufficient to prove these semantics.
- No calculation runs from a cron process or API startup hook.

## 29. Recommended Implementation Order

1. Canonical weight migration and compatibility tests.
2. Nutrition completion status and automatic downgrade behavior.
3. Target provenance migration.
4. Adaptive tables and schemas.
5. Pure algorithm and deterministic fixtures.
6. Read aggregation and eligibility service.
7. Preview/fingerprint/check-in persistence.
8. Acceptance/decline transactions and invalidations.
9. Coach setup and state UI.
10. Nutrition completion UI.
11. History and calculation detail UI.
